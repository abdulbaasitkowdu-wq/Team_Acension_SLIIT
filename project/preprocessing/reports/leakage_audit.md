# Data leakage audit

## Conclusion

The implemented offline path produces **16 candidate features for 1,164,472 retained transactions**. I found no target or fraud outcome columns in that feature list, no future event values in its historical calculations, and no shared transaction keys, exact duplicate records, or batch-level fraud records across the retained splits.

The release supports retrospective experiments. It does not establish when event readings, catalogue versions, or confirmed fraud labels became available to a live scorer. The upstream cleaning and integration workflows also contain release-wide checks that would block a live run without audit data. The frozen evaluation excludes whole batches using their eventual last event, and every split contains the same manufacturers. These limitations affect what a later score can claim. The proposed corrections below were not applied.

## Scope and verification

Reviewed all six notebooks in `notebooks/`, all three modules in `src/`, the feature tests, the feature audit CSV, the prediction design, the split artifacts, and the supplied dataset generator, configuration, and validator. Every notebook had valid saved execution outputs. I verified the frozen assignment and input checksums, matched the binary target to its original value on every composite key, reproduced the integration and feature build in memory, and reran all four feature tests. I independently recomputed each historical feature on 195 rows, spread across the three retained splits, using an explicit filter for strictly earlier events in the same batch. All comparisons passed. New feature-to-label checks were restricted to training data. The supplied generator and legacy validator were inspected as source code.

| Check | Finding |
| --- | --- |

| Future transaction information | No later or simultaneous event contributes to an earlier historical feature. Event arrival times and historical field availability are unverified. |

## Findings and proposed corrections

### 1. Retrospective outcome data are required by upstream archive cleaning

The transaction archive schema requires `is_fraud_ground_truth`, `is_masked`, `is_suspicious_genuine`, and `is_fraud_detected`. Validation checks whether `fraud_type` is populated exactly when ground truth is true. The cleaning notebook also prepares `fraud_events` and checks every transaction label against the saved target. This is appropriate release QA. It would make a live feature pipeline depend on future outcomes if reused unchanged. The clean archive still contains those columns, so reading it as a model matrix would leak the answer. The active integration projection explicitly excludes them, and `fraud_events.in_ring` is used only in the split audit. [Cleaning schema and required values](../src/cleaning.py#L35) · [Required-column enforcement](../src/cleaning.py#L199) · [Fraud consistency check](../src/cleaning.py#L240) · [Notebook 04, In 3](../notebooks/04_Data_Cleaning.ipynb) · [Integration projection](../src/integration.py#L7) · [Notebook 02, In 4](../notebooks/02_Target_and_Data_Splitting.ipynb)

**Proposed correction.** Keep archive cleaning and the batch fraud consistency checks as an offline quality job. Define a separate scoring schema and validation path that accepts only approved observations and does not require any outcome field or target file. Test that path with every outcome column and the fraud table absent. In later notebooks, select the explicit model feature list and attach `y` separately by transaction key. `batch_id`, `timestamp`, and `split` are metadata in the engineered frame. Avoid using the entire frame as `X`. [Engineered feature list and output columns](../src/features.py#L15) · [Notebook 06, In 3](../notebooks/06_Feature_Engineering.ipynb)

### 2. Event time and label availability are separate

Features use `transactions.timestamp` as the score time. The release contains no timezone, arrival clock, or field-level revision times. The historical implementation sorts by recorded timestamp, aggregates whole `(batch_id, timestamp)` groups, and shifts state before emitting that group's features. The existing tests verify both future-record invariance and exclusion of current and tied rows. This proves causality with respect to the recorded event clock, under the offline assumption that the readings were available when the events were scored. A backfilled `humidity`, `weight`, `rfid_scanned`, or `door_open` value could have an earlier event time and still arrive after the score in a live workflow. [Feature history](../src/features.py#L29) · [Feature input contract and sort](../src/features.py#L61) · [Future and tie tests](../tests/test_features.py#L48) · [Prediction design](prediction_design.md#prediction-timestamp)

The generator assigns `is_fraud_ground_truth` once per batch and separately samples `is_fraud_detected` from it. There is no investigation confirmation timestamp or delay for either field. The split metadata correctly records cutoff availability as unknown at both **2025-05-16 13:07:41** and **2025-09-02 13:42:03**. A complete retrospective label is insufficient to prove it was known at a past fitting date. [Generator, assignment](../Phase1_Dataset/code/generator.py#L184) · [Generator, detection](../Phase1_Dataset/code/generator.py#L299) · [Notebook 02, In 3](../notebooks/02_Target_and_Data_Splitting.ipynb) · The split notebook generates the local `processed/split_boundaries.json`.

**Proposed correction.** For a prospective replay, capture a timezone-aware scoring clock, field or record arrival/version times, and actual label confirmation times. Require historical event time to be strictly earlier than the score and the input version to be available by the score. For each fit, use labels confirmed by its cutoff and keep pending labels out of training. Treat the existing evaluation as retrospective until those times exist.

### 3. Fixed catalogue inputs pass the offline check. The verification gate spans all periods.

All 300 catalogue rows match the fixed storage configuration. The audit reproduced `rolling_excursion_rate` on all 1,201,800 source events with current and earlier `temperature` readings in batch order. The joins preserved 60,000 rows at each batch-level lookup and 1,201,800 at the event join, with zero unmatched keys. The final model inputs receive `is_cold_chain` and the width of the validated `storage_min` and `storage_max` interval. Changing entity and price snapshots remain excluded. The `production_date` check is day-level and there were zero earlier events. It does not establish when a live feed published a batch record or catalogue version. [Join validation](../src/integration.py#L37) · [Timing and catalogue checks](../src/integration.py#L71) · [Lookup path and output projection](../src/integration.py#L116)

`temperature`, `rolling_excursion_rate`, and `batch_tx_index` enter the integration verification gate. They are excluded from all final features. Notably, a corrupted future row can still abort the entire feature workflow because Notebook 06 calls the release-wide gate before selecting rows. That changes whether the offline job completes. It does not let later readings change the value of an earlier output feature. No rule or cutoff was learned from those audit fields. [Audit-only columns](../src/integration.py#L16) · [Storage gate](../src/integration.py#L94) · [Notebook 06, In 3](../notebooks/06_Feature_Engineering.ipynb)

**Proposed correction.** Move the release-wide storage check into an offline certification step, then consume a versioned, approved catalogue mapping in the scoring path. Keep `temperature`, the stored rate and the stored sequence index out of that path. For mutable fields such as `license_status`, `audit_score`, `gmp_compliant`, `customs_clearance`, or `price`, keep the current holdout until the effective version and its availability at scoring can be verified. Add a test where a late catalogue revision cannot change any earlier prediction.

### 4. Time and batch isolation pass. The cohort definition uses future event times.

The retained train, validation, and test sets contain 831,536, 161,976, and 170,960 rows. Batch-level ground truth is copied onto all events, and those batches are disjoint. There is no incident ID to check related fraud spanning separate batches. All **23 manufacturers** and **300 medicine IDs** occur in all three sets. One manufacturer flagged through `in_ring` is shared by each pair of splits. The March–May 2025 configured campaign covers 5,555 training and 1,408 validation batches, with none in test. These are production-date window counts. The release does not expose true incident, campaign, or ring identifiers. [Notebook 02, In 4](../notebooks/02_Target_and_Data_Splitting.ipynb) · [Campaign and ring configuration](../Phase1_Dataset/code/config.yaml#L93) · [Generator, ring and campaign mechanics](../Phase1_Dataset/code/generator.py#L167)

The split generator removes all rows of a batch when its *eventual* last event crosses either cutoff. The resulting freeze excludes 37,328 rows from 1,536 batches. By timestamp alone, 9,724 of those rows were in the nominal training window, 18,294 in validation, and 9,310 in test. This is a target-free retrospective cohort decision. A scorer would not yet know at those events that their batch would cross a cutoff. The frozen primary evaluation therefore describes later events in retained non-straddling batches. [Notebook 02, In 2](../notebooks/02_Target_and_Data_Splitting.ipynb) · [Notebook 06, In 3](../notebooks/06_Feature_Engineering.ipynb)

**Proposed correction.** Keep the existing split fixed for comparable results and disclose the exclusion. Add a separately specified chronological replay with a batch-entry or eligibility rule based on information known at the scoring time if claiming live performance. Report crossing batches explicitly in that replay. Require a manufacturer-disjoint or whole-campaign holdout before claiming performance on unseen manufacturers or campaigns. Use a separate product holdout if claiming performance on unfamiliar products.

### 5. The simulator produces strong shortcuts and the bundled validator bypasses the safeguards

A training-only check of the release found **7,185 fraud and zero genuine rows** with `seal_intact=False`. Missing `gps_lat` occurred in 21,459 fraud and 7,439 genuine training rows. Failed `qr_verified` occurred in 27,714 fraud and 44,960 genuine rows. The supplied generator also injects temperature excursions in some cold-chain fraud, uses manufacturer licence/compliance/audit inputs to influence fraud assignment, and applies production-date campaign boosts. Those mechanics justify holding out `seal_intact`, `qr_verified`, both GPS fields and their missingness, `temperature`, derivative excursion values, the raw production calendar, direct manufacturer risk inputs, and `expiry_date` combined with `shelf_life_days`. The release-only `duplicate_serial` and `cumulative_excursion_time` remain unsafe until their construction and timing are verified. Relative elapsed times and prior counts can still reflect the simulator's fixed lifecycle and generated cadence, although their arithmetic excludes future events. [Fraud assignment](../Phase1_Dataset/code/generator.py#L184) · [Evidence rules](../Phase1_Dataset/code/generator.py#L232) · [Batch dates](../Phase1_Dataset/code/generator.py#L149) · [Feature audit](feature_audit.csv#L47)

The bundled `validate.py` is outside the active pipeline. It trains on `is_fraud_detected` with a random row split and uses `seal_intact`, `qr_verified`, GPS missingness, temperature, the stored excursion rate and sequence index, `audit_score`, and `gmp_compliant`. This can share related events across sets, use shortcuts, and answer a different prediction question. [Bundled validator feature matrix and target](../Phase1_Dataset/code/validate.py#L76) · [Bundled random row split](../Phase1_Dataset/code/validate.py#L102)

**Proposed correction.** Preserve the current holdouts and explicitly mark the bundled validator as a generator diagnostic in project instructions. Use subgroup or validation-only ablation checks of storage profile and simulated lifecycle features before making real-world claims. Keep the test set sealed for the final evaluation.

### 6. Held-out class totals are visible. The derived features need a machine-readable audit.

Notebook 01 computes full-release descriptive statistics for schema QA. Its first five stored transaction rows, batch rows, and fraud table rows all mapped to training in this frozen release. Their selection was based on storage order, which would not protect previews on reruns with a different release. Notebook 02 computes and stores held-out class totals and compares labels to the fraud table for integrity. Notebook 03 filters to training before any label relationships, outlier fences, or correlations. Notebook 04 uses documented domains and fixed casts. Notebooks 05 and 06 use an explicit list and structural checks. I found no full-dataset fitting, no resampling, and no feature choice based on validation or test labels. [Notebook 01 preview and profile, In 2](../notebooks/01_Data_Understanding.ipynb) · [Notebook 02 split totals, In 2 and In 5](../notebooks/02_Target_and_Data_Splitting.ipynb) · [Saved class totals](../notebooks/02_Target_and_Data_Splitting.ipynb) · [Notebook 03 training filter, In 1](../notebooks/03_Exploratory_Data_Analysis.ipynb) · [Fixed cleaning domains](../src/cleaning.py#L63)

The eight directly copied features appear in `feature_audit.csv`. The eight derived features are documented in Notebook 06 and listed in code, but the CSV currently covers released input columns only. The review below traces those features to the existing CSV entries. A future change to the derived features is not yet checked against a machine-readable list of approved dependencies. [Notebook 06 definitions](../notebooks/06_Feature_Engineering.ipynb) · [Feature list](../src/features.py#L15)

**Proposed correction.** Keep held-out outcome summaries in an audit-only artifact and restrict row previews involving labels to the frozen training manifest. Add a derived-feature register linked to the raw audit, and enforce it in the estimator input loader. For later learned encoders, imputers, scalers or selectors, test that the fit uses only training rows and that validation/test targets stay out of feature selection.
